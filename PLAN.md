## 2. Общий план: что, зачем, какие технологии

### Общая архитектура

```
Клиент → API Gateway (YARP) → Identity / Catalog / Orders / Inventory / Payment / Notifications
                                     ↕ HTTP (синхронно)    ↕ RabbitMQ (асинхронно)
```

Каждый сервис устроен по **Clean Architecture**:

```
Catalog.Api             → HTTP: контроллеры, DI, Swagger
Catalog.Infrastructure  → БД: EF Core, репозитории
Catalog.Application     → сценарии: сервисы, DTO, интерфейсы, валидация
Catalog.Domain          → бизнес-правила: сущности, исключения
```

**Правило зависимостей:** `Api → Infrastructure → Application → Domain`. Стрелки идут только внутрь. Domain ничего не знает ни про БД, ни про веб, поэтому его легко тестировать, а технологии вокруг можно менять.

### Этап 0. Подготовка ✅ (почти)
- **Что:** solution, проекты, `global.json`, `Directory.Build.props`, Git.
- **Зачем:** проект собирается одинаково на любой машине (версия SDK зафиксирована), общие настройки в одном месте, история изменений с первого дня.
- **Технологии и подходы:** .NET CLI, MSBuild, Git, небольшие осмысленные коммиты.

### Этап 1. Catalog — фундамент
Задача этапа — научиться делать **один** сервис правильно. Остальные сервисы строятся по тому же шаблону.

#### 1.1 Domain ← сейчас
- **Что:** `Product`, `Category`, `ProductImage`, `DomainException`.
- **Зачем:** бизнес-правила живут в одном месте, и их невозможно обойти. Объект нельзя создать или привести в некорректное состояние.
- **Подходы:** DDD (тактические паттерны): богатая модель вместо анемичной, инварианты, агрегат и корень агрегата, Value Object. Инкапсуляция (`private set`, `IReadOnlyCollection`), guard clauses, fail fast.

#### 1.2 Infrastructure
- **Что:** PostgreSQL в Docker, `CatalogDbContext`, конфигурации сущностей, миграции, реализация репозитория.
- **Зачем:** сохранение в БД отделено от бизнес-логики (**Persistence Ignorance**). Domain не знает, что есть EF Core.
- **Технологии:** Docker Desktop + Docker Compose, EF Core (Code First), Npgsql, Fluent API (`IEntityTypeConfiguration<T>`), миграции, `HasQueryFilter` для мягкого удаления, **фильтрованный** уникальный индекс на `Sku` (только среди неудалённых), `HasPrecision` для `decimal`, оптимистическая блокировка (`xmin` в PostgreSQL), ограничения длины колонок, `SaveChangesInterceptor` для автоматических `CreatedAt`/`UpdatedAt` (заменит `MarkUpdated()`).
- **Сделать заранее:** установить Docker Desktop (нужен WSL2).

#### 1.3 Application
- **Что:** `IProductRepository`, DTO, `ProductService` (создать, получить, изменить, удалить), валидация.
- **Зачем:**
  - Интерфейс репозитория здесь, реализация в Infrastructure: **Dependency Inversion** (D из SOLID). Бизнес-логика зависит от абстракции, а не от EF.
  - DTO, чтобы не отдавать сущности наружу. Клиент не видит внутреннее устройство и не может прислать лишние поля (**over-posting**).
  - **Два уровня валидации:** FluentValidation проверяет формат запроса (поле заполнено, длина), домен проверяет бизнес-правила (удалённый товар менять нельзя).
- **Технологии:** FluentValidation, маппинг (вручную или Mapster), DI.

#### 1.4 Api
- **Что:** 5 REST-эндпоинтов, обработка ошибок, документация.
- **Зачем:** договор с внешним миром — правильные методы, коды статусов, единый формат ошибок.
- **Технологии:** ASP.NET Core (контроллеры), REST, пагинация, `ProblemDetails` (RFC 9457), `IExceptionHandler` (`DomainException` → 400), Swagger/OpenAPI, `CancellationToken`.

| Метод | Маршрут | Ответ |
|---|---|---|
| GET | `/api/products?page=1&pageSize=20&categoryId=..&search=..` | 200 + страница |
| GET | `/api/products/{id}` | 200 / 404 |
| POST | `/api/products` | 201 + заголовок `Location` |
| PUT | `/api/products/{id}` | 204 / 404 |
| DELETE | `/api/products/{id}` | 204 / 404 |

#### 1.5 Тесты
- **Что:** unit-тесты на домен и сервис (5–10 штук для начала).
- **Зачем:** уверенность, что правила работают, и возможность смело рефакторить.
- **Технологии:** xUnit, AAA (Arrange–Act–Assert), NSubstitute/Moq. Позже — интеграционные тесты на Testcontainers.

**Критерий готовности этапа 1:** БД поднимается с нуля по README, все эндпоинты отдают правильные коды статусов, невалидный запрос даёт 400 с `ProblemDetails`, тесты зелёные, всё в git небольшими коммитами.

### Этап 2. Identity + API Gateway
- **Что:** сервис регистрации и входа, единая точка входа.
- **Зачем:** аутентификация в одном месте, а не в каждом сервисе. Клиент знает один адрес, а не пять.
- **Технологии:** JWT (access + refresh), роли и политики, ASP.NET Core Identity, YARP, rate limiting.

### Этап 3. Orders + синхронное общение
- **Что:** сервис заказов; при создании заказа он по HTTP спрашивает у Catalog цену и наличие.
- **Зачем:** научиться работать с ненадёжной сетью (сервис недоступен, отвечает медленно, падает).
- **Технологии:** `HttpClientFactory`, typed clients, Polly / `Microsoft.Extensions.Http.Resilience` (retry, circuit breaker, timeout). **CQRS + MediatR** с pipeline behaviors. По желанию — gRPC.

### Этап 4. Асинхронное общение
- **Что:** RabbitMQ, события (`OrderCreated` и др.), сервис Notifications как подписчик.
- **Зачем:** сервисы не ждут друг друга (**слабая связанность**); данные согласуются не мгновенно (**eventual consistency**).
- **Технологии:** RabbitMQ, MassTransit, publish/subscribe, идемпотентные обработчики, паттерн **Strategy** (email / SMS / консоль).

### Этап 5. Saga + Outbox + Inventory + Payment
- **Что:** заказ проходит цепочку «резерв товара → оплата»; если шаг упал, предыдущие откатываются.
- **Зачем:** в микросервисах нет одной транзакции на несколько баз. Главная тема для Middle+.
- **Технологии:** **Saga** (MassTransit State Machine), компенсирующие действия, **Transactional Outbox**, оптимистическая блокировка (`RowVersion`). `Stock` переезжает из Catalog в Inventory.

### Этап 6. Наблюдаемость и CI
- **Что:** логи, трассировка, health checks, запуск одной командой, автосборка.
- **Зачем:** в распределённой системе без этого невозможно понять, где сломался запрос.
- **Технологии:** Serilog, OpenTelemetry + Jaeger/Seq, Health Checks, Docker Compose для всего стека, GitHub Actions.

## 3. Этап 1.1 Domain: инструкция

### Главная цель
Объект **невозможно создать или привести в некорректное состояние**. Если конструктор или метод отработал без исключения, объект валиден.

### Жизненный цикл Product (не только создание!)
`Product` работает на **каждом** запросе, а не только при создании нового товара:

| Запрос | Что происходит с `Product` |
|---|---|
| POST (создать) | `new Product(...)` — публичный конструктор проверяет данные → сохранить |
| GET (прочитать) | EF загружает из БД через `private Product()` и заполняет свойства → маппинг в DTO |
| PUT (изменить) | загрузить → `product.ChangeDetails(...)` / `ChangePrice(...)` → сохранить. EF сам видит изменённые свойства и делает `UPDATE` |
| DELETE | загрузить → `product.Delete()` → сохранить |

Сервис **не меняет поля сам**, он только вызывает методы товара. Поэтому правила работают при любом изменении, а не только при создании.

### Конструкторы
1. **`private Product() { }`** — пустой, только для EF Core.
2. **`public Product(name, description, price, stock, categoryId, sku)`** — только то, что задаёт пользователь:
   - `Id = Guid.NewGuid();`
   - каждое значение проверяется и присваивается (передаются **параметры**, а не свойства)
   - `CreatedAt = DateTime.UtcNow;`
   - **не** принимает `createdAt`, `updatedAt`, `isDeleted`, список картинок: новый товар всегда создан сейчас, не обновлялся, не удалён и без картинок

**Как это работает с `private`:** модификатор доступа проверяется **по месту вызова**. Конструктор — код внутри класса, поэтому он может вызывать `private`-методы и писать в `private set`. Снаружи (в сервисе) доступно только то, что `public`: `new Product(...)` и методы `Change...`. EF Core обходит `private` через рефлексию.

*(По желанию)* Вместо публичного конструктора в DDD часто делают фабричный метод `public static Product Create(...)` + `private` конструктор. Плюсы: понятное имя, позже можно возвращать `Result` вместо исключения.

### DomainException

Файл `Catalog.Domain/DomainException.cs`:

```csharp
namespace Catalog.Domain;

public class DomainException : Exception
{
    public DomainException(string message) : base(message) { }
}
```

- Своё исключение = **нарушено бизнес-правило**. На шаге 1.4 `IExceptionHandler` превратит именно его в **400** с `ProblemDetails`, а любое другое исключение — в **500** (ошибка в коде).
- `: base(message)` передаёт текст в `Exception.Message`.
- Не `sealed`: позже можно сделать наследников (`InsufficientStockException : DomainException`), и обработчик поймает их всех.
- Сериализационный конструктор и `[Serializable]` **не нужны**: в .NET 8+ это устаревший механизм (SYSLIB0051).
- Использование: `throw new DomainException("Цена должна быть больше нуля");`. `nameof(...)` больше не нужен — текст для человека, а не имя параметра.

### Свойства

| Свойство | Тип | Примечание |
|---|---|---|
| `Id` | `Guid` | |
| `Name` | `string` + `= null!` | обязательное, ≤ 200 символов |
| `Description` | `string?` | необязательное |
| `Price` | `decimal` | > 0 (или ≥ 0, если бывают бесплатные) |
| `Stock` | `int` | ≥ 0 |
| `CategoryId` | `Guid` | не `Guid.Empty` |
| `Sku` | `string` + `= null!` | артикул, ≤ 50 символов |
| `CreatedAt` | `DateTime` | UTC |
| `UpdatedAt` | `DateTime?` | UTC, `null` у нового товара |
| `IsDeleted` | `bool` | мягкое удаление |
| `DeletedAt` | `DateTime?` | UTC, когда удалён; `null`, если не удалён |
| `Images` | `IReadOnlyCollection<ProductImage>` | через закрытое поле `List<ProductImage> _images` |

#### `= null!` — что это и куда ставить
- `string` = обещание «никогда не `null`», `string?` = «может быть `null`» (включено через `<Nullable>enable</Nullable>`).
- Компилятор проверяет, что после **каждого** конструктора у не-nullable свойств есть значение. Внутрь вызываемых методов (`SetName`) он **не заглядывает**, а EF-конструктор вообще ничего не присваивает → warning CS8618.
- `null!` — оператор «прощения null» (`!`): «сейчас здесь `null`, но я гарантирую, что значение появится до чтения» (его запишет `SetName` в конструкторе или EF из БД).
- Ставится в объявлении свойства: `public string Name { get; private set; } = null!;`
- **Куда:** только не-nullable `string` (и другие ссылочные типы), которые заполняются через методы или EF: `Product.Name`, `Product.Sku`, `ProductImage.PathImage`, `ProductImage.NameImage`, `Category.Name`.
- **Куда НЕ ставить:** `string?` (там `null` и так разрешён), значимые типы (`Guid`, `int`, `decimal`, `DateTime`, `bool` — они не бывают `null`), `_images` (уже инициализирован).
- `null!` — это обещание. Не ставь его, чтобы просто «заглушить» предупреждение там, где значение действительно может не появиться.
- **`string?` — не замена `= null!`.** Вопрос один: **может ли значение законно отсутствовать?** Да (описание) → `string?`. Нет (название, артикул, путь к картинке) → `string` + `= null!`. Предупреждение от `string?` тоже исчезнет, но смысл изменится: EF создаст nullable-колонку, а весь код будет вынужден проверять `null` там, где его быть не должно.

### Общие правила для методов

Каждый публичный метод, который **меняет** товар, проходит 4 шага:

```csharp
public void ChangePrice(decimal newPrice)
{
    EnsureNotDeleted();      // 1. можно ли вообще менять объект
    ValidatePrice(newPrice); // 2. корректны ли новые данные
    Price = newPrice;        // 3. меняем состояние
    MarkUpdated();           // 4. фиксируем факт изменения
}
```

Помощники (пишутся один раз):

```csharp
private void EnsureNotDeleted()
{
    if (IsDeleted)
        throw new DomainException("Нельзя изменить удалённый товар");
}

private void MarkUpdated() => UpdatedAt = DateTime.UtcNow;
```

- **Проверки** — `private static void ValidateXxx(...)`: только проверяют и бросают `DomainException`. `static`, потому что не зависят от состояния объекта. Используются и в конструкторе, и в методах.
- **Конструктор** вызывает только `Validate...` и присваивает (без `EnsureNotDeleted` и `MarkUpdated`: объект только рождается).
- **`Delete()`** идемпотентный: если уже удалён, просто `return`. HTTP DELETE тоже идемпотентен.
- **Подходы:** guard clauses / fail fast, DRY.
- **`UpdatedAt` — решение:** сейчас `MarkUpdated()` в сущности (просто, работает без БД, можно проверить в тестах). На шаге 1.2 переносим в Infrastructure: `SaveChangesInterceptor` проставляет `CreatedAt`/`UpdatedAt` всем изменённым сущностям, а `MarkUpdated()` удаляем. Главное правило: дата ставится **в одном месте**, никогда не в сервисах.

### Validate-методы: одно правило — одно место

Каждое значение, которое **входит** в объект (через конструктор или через метод), проверяется. Чтобы правило не дублировалось, проверка выносится в отдельный метод:

```csharp
public const int MaxNameLength = 200;

private static void ValidateName(string name)
{
    if (string.IsNullOrWhiteSpace(name))
        throw new DomainException("Название товара не может быть пустым");
    if (name.Length > MaxNameLength)
        throw new DomainException($"Название товара не длиннее {MaxNameLength} символов");
}
```

Использование:
- в конструкторе: `ValidateName(name); Name = name;`
- в `ChangeDetails`: `EnsureNotDeleted(); ValidateName(name); Name = name; ... MarkUpdated();`

Почему `static`: в статическом методе **нельзя обратиться к свойствам объекта**, поэтому ошибка вида «проверил `CategoryId` вместо `categoryId`» становится невозможной — компилятор не даст.

Почему `public const`: тот же лимит понадобится в EF-конфигурации (`HasMaxLength`) и в FluentValidation. Одно число — в одном месте.

Полный набор для `Product`:

| Метод | Правило | Где вызывается |
|---|---|---|
| `ValidateName` | не пустое, ≤ `MaxNameLength` | конструктор, `ChangeDetails` |
| `ValidateDescription` | `null` можно, но ≤ ~2000 | конструктор, `ChangeDetails` |
| `ValidatePrice` | > 0 | конструктор, `ChangePrice` |
| `ValidateStock` | ≥ 0 (начальный остаток) | конструктор |
| `ValidateQuantity` | > 0 (сколько добавить/списать) | `AddStock`, `RemoveStock` |
| `ValidateCategoryId` | не `Guid.Empty` | конструктор, `ChangeCategory` |
| `ValidateSku` | не пустой, ≤ ~50 | конструктор |

Публичные `SetName`, `SetPrice`, `SetStock`, `SetCategory`, `SetSku` после этого **удаляются**: их заменяют бизнес-методы ниже.

**Допустимый вариант:** оставить `SetName` и т. д., но сделать их **`private`** (проверка + присваивание в одном методе). Это тоже работает. Условия:
- `private`, иначе снаружи можно изменить товар в обход `EnsureNotDeleted()` и `MarkUpdated()`;
- внутри `Set...` **никогда** не вызывать `MarkUpdated()` (их вызывает конструктор, а у нового товара `UpdatedAt == null`);
- проверять только параметр (метод не `static`, компилятор от ошибки «свойство вместо параметра» не защитит).

Выбери один вариант и используй его для всех свойств.

### Что можно менять после создания

| Свойство | Меняется? | Через что |
|---|---|---|
| `Id`, `CreatedAt` | никогда | — |
| `Name`, `Description` | да | `ChangeDetails` |
| `Price` | да | `ChangePrice` |
| `Stock` | да | `AddStock` / `RemoveStock` |
| `CategoryId` | да | `ChangeCategory` |
| `Sku` | **нет** (решение) | артикул — идентификатор для склада, заказов, документов. Если бизнес попросит — `ChangeSku` + проверка уникальности в сервисе |
| `IsDeleted`, `DeletedAt` | только через методы удаления | `Delete()`, *(по желанию)* `Restore()` |

### Как группировать методы: по бизнес-операциям

Не «один метод на всё» и не «метод на каждое свойство», а **метод на каждое действие, которое реально делают люди**. Вопрос для проверки: **кто и зачем это меняет?**

| Действие | Кто | Метод | Почему отдельно |
|---|---|---|---|
| Поправить название и описание | контент-менеджер | `ChangeDetails(name, description)` | меняются вместе по одной причине |
| Изменить цену | менеджер по ценам | `ChangePrice(price)` | позже: история цен, событие `PriceChanged` для корзин и заказов |
| Пришёл / списан товар | склад | `AddStock` / `RemoveStock` | своя логика («хватает ли»), на этапе 5 уедет в Inventory |
| Перенести в другую категорию | контент-менеджер | `ChangeCategory(categoryId)` | отдельное решение, позже: проверка, что категория существует |
| Удалить | админ | `Delete()` | важное действие, отдельные права; свои правила (см. «Удаление товара») |

**Почему не один `Update(всё сразу)`:** смешиваются разные операции. Через такой метод можно «обновить» остаток в обход `RemoveStock`, не видно, что именно поменялось (нельзя отправить `PriceChanged`), и нельзя дать разным ролям разные права.

**Почему не метод на каждое свойство:** это те же сеттеры, только с проверкой. Название и описание по смыслу правят вместе, разбивать их — лишняя детализация.

**Принцип:** high cohesion / SRP — вместе меняется то, что меняется по одной причине. В API это называется **task-based** подход (в отличие от чистого CRUD).

**Как это стыкуется с PUT:** один PUT может вызвать в сервисе несколько методов подряд: `ChangeDetails` → `ChangePrice` → `ChangeCategory`. **Остатка в PUT нет**: он меняется отдельными эндпоинтами (например `POST /api/products/{id}/stock` с количеством) — это решим на шаге 1.4.

### Бизнес-методы Product

| Метод | Что делает | Что проверяет |
|---|---|---|
| `ChangeDetails(name, description)` | меняет имя и описание | имя не пустое, длина |
| `ChangePrice(newPrice)` | меняет цену | правило цены |
| `AddStock(quantity)` | приход товара | `quantity > 0` |
| `RemoveStock(quantity)` | списание | `quantity > 0`, остатка хватает |
| `ChangeCategory(categoryId)` | меняет категорию | не `Guid.Empty` |
| `Delete()` | `IsDeleted = true`, `DeletedAt = UtcNow` | идемпотентный |
| `AddImage(fileName, url)` | сам создаёт `ProductImage` со своим `Id` | лимит, например ≤ 10 |
| `RemoveImage(imageId)` | удаляет картинку | картинка существует |

Почему не `SetStock(5)`: метод должен описывать **бизнес-действие** («пришёл товар», «списали»), а не «записать число». Тогда правило «хватает ли остатка» живёт внутри объекта, и его невозможно забыть.

### Удаление товара

#### Зачем мягкое удаление (soft delete), а не `DELETE` из БД
- **Заказы ссылаются на товар.** Если физически удалить строку, старые заказы потеряют связь с товаром (или БД не даст удалить из-за внешнего ключа).
- **Можно восстановить** товар, удалённый по ошибке.
- **История и аудит:** видно, что товар был и когда его удалили.

#### Что добавить в `Product`
1. Свойство **`DeletedAt`** (`DateTime?`, `private set`) — когда удалён. На этапе 2 можно добавить `DeletedBy` (кто).
2. Метод **`Delete()`**:
   - если уже удалён → просто `return` (идемпотентность: повторный HTTP DELETE не даёт ошибку);
   - *(решение)* проверка бизнес-правила, см. ниже;
   - `IsDeleted = true`, `DeletedAt = DateTime.UtcNow`.
   - `EnsureNotDeleted()` здесь **не вызывается** — иначе повторное удаление бросит исключение.
3. Помощник **`EnsureNotDeleted()`** — первой строкой в **каждом** методе, который меняет товар: `ChangeDetails`, `ChangePrice`, `ChangeCategory`, `AddStock`, `RemoveStock`, `AddImage`, `RemoveImage`, `Publish`/`Unpublish`.
4. *(по желанию)* **`Restore()`**: если не удалён → `return`; `IsDeleted = false`, `DeletedAt = null`, `MarkUpdated()`.

#### Бизнес-решения (выбери и запиши сюда)
| Вопрос | Варианты | Рекомендация |
|---|---|---|
| Можно ли удалить товар, у которого `Stock > 0`? | запретить (`DomainException`: «сначала спишите остаток») или разрешить | запретить — меньше «потерянного» товара на складе |
| Что с картинками при удалении? | удалить или оставить | оставить — нужны для `Restore()` |
| Опубликованный товар (если есть `Status`)? | снять с публикации автоматически или запретить удаление | снять автоматически |

#### Что **не** проверяется
- **Чтение** (`get` свойств) — разрешено и у удалённого товара (админке нужно его показать).
- **`Delete()`** сам по себе (см. выше).

#### Как это проявится на следующих шагах
- **1.2 Infrastructure:** `HasQueryFilter(p => !p.IsDeleted)` — удалённые товары исчезают из **всех** запросов автоматически. Для админки — `IgnoreQueryFilters()`.
- **1.2 Infrastructure:** уникальный индекс на `Sku` должен быть **фильтрованным** (только среди неудалённых), иначе удалённый товар навсегда «занимает» артикул.
- **1.3 Application:** из-за фильтра сервис просто не найдёт удалённый товар → 404. `EnsureNotDeleted()` в сущности — **вторая линия защиты** (defense in depth), если кто-то загрузит товар в обход фильтра.
- **1.4 Api:** `GET` / `PUT` удалённого → 404; `DELETE` удалённого → 204 (идемпотентность).

#### Тесты на удаление (шаг 1.5)
- `Delete()` выставляет `IsDeleted = true` и `DeletedAt`.
- Повторный `Delete()` не бросает исключение и не меняет `DeletedAt`.
- `ChangePrice` / `ChangeDetails` / `AddStock` после `Delete()` → `DomainException`.
- `Delete()` товара с остатком > 0 → `DomainException` (если выбрал «запретить»).
- *(если есть)* `Restore()` возвращает товар, и его снова можно менять.

### Методы по желанию

#### Публикация: `Publish()` / `Unpublish()`
- `enum ProductStatus { Draft, Published, Archived }`, свойство `Status`, новый товар — `Draft`.
- `Publish()`: нельзя для удалённого товара и для товара без картинок.
- `Unpublish()`: вернуть в `Draft`.
- **Учит:** машине состояний (State machine) — разрешены только определённые переходы. На этапе Orders статусов будет больше.
- **Где пригодится:** витрина показывает только `Published`, админка — все.

#### Главная картинка: `SetMainImage(imageId)`
- В `ProductImage`: `bool IsMain` и `internal` методы `MarkAsMain()` / `UnmarkAsMain()`.
- **Инвариант:** если картинки есть, главная ровно одна.
  1. `AddImage`: первая картинка автоматически становится главной.
  2. `SetMainImage`: снять флаг с текущей, поставить на новую (нет такой — исключение).
  3. `RemoveImage`: удалили главную → главной становится первая из оставшихся.
- **Учит:** зачем нужен агрегат. Правило касается всех картинок сразу, и гарантировать его может только `Product`.

#### Value Object `Money` (после всего этапа 1)
- `public record Money(decimal Amount, string Currency)` с проверками в конструкторе.
- Решает **Primitive Obsession**: нельзя случайно сложить рубли с долларами.
- Entity сравнивается по `Id` и меняется; Value Object сравнивается по значению и **неизменяем**.
- В EF Core: `ComplexProperty` или `OwnsOne` (две колонки в таблице `Products`).

### Чего НЕ делать в Domain
- **Уникальность `Sku`:** `Product` не знает о других товарах. Это уникальный индекс в БД + проверка в Application.
- **Работа с БД, HTTP, логирование** — это Infrastructure / Api.
- **`Stock`** пока остаётся в Catalog, на этапе 5 переедет в Inventory.

### Агрегат Product
- `Product` — **корень агрегата**. `ProductImage` существует только внутри него и меняется только через его методы.
- `Category` — **отдельный агрегат**. `Product` хранит только `CategoryId`.

## 4. Куда класть логику

Мы работаем по **Clean Architecture + DDD (тактические паттерны)** с **богатой доменной моделью** (Rich Domain Model). Каждый слой отвечает за своё:

| Вопрос | Где | Пример |
|---|---|---|
| Касается только данных **этого объекта**? | **Entity** (Domain) | «цена > 0», «остатка хватает на списание», «удалённый товар не менять» |
| Нужна БД, другой сервис, несколько агрегатов, транзакция? | **Application Service** | «артикул уникален», «загрузить товар → вызвать метод → сохранить» |
| Это формат входящего запроса? | **Validator** (FluentValidation, Application) | «поле `name` заполнено», «`pageSize` от 1 до 100» |
| Это про HTTP? | **Controller** (Api) | коды статусов, маршруты, заголовок `Location` |
| Это про хранение? | **Repository / DbContext** (Infrastructure) | SQL, индексы, миграции |

**Типичный сценарий в Application Service** (появится на шаге 1.3):
1. Загрузить товар из репозитория (нет — 404).
2. Вызвать **метод сущности**: `product.ChangePrice(request.Price)`. Правила проверит сама сущность.
3. Сохранить через репозиторий.
4. Вернуть DTO.

Сервис **оркестрирует** (что, когда, с какой инфраструктурой), сущность **решает** (можно ли и как).

**Сервис не заменяет методы сущности, он их вызывает.** У свойств `private set`, поэтому `product.Name = "..."` в сервисе — ошибка компиляции (CS0272). Методы вроде `ChangeDetails` — единственная «дверь» для изменения данных, и в этой двери стоит проверка.

**Аналогия:** банкомат (сервис) не меняет баланс счёта напрямую. Он вызывает `account.Withdraw(1000)`, а счёт (сущность) сам проверяет, хватает ли денег. Банкоматов, приложений и касс может быть много, а правило одно — внутри счёта.

**Кто что делает при `PUT /api/products/{id}`:**

| Слой | Что делает |
|---|---|
| Controller | принимает JSON, вызывает сервис, возвращает 204 / 404 / 400 |
| Validator | формат: поля заполнены, длина |
| ProductService | загрузить товар (нет — 404) → `product.ChangeDetails(...)`, `product.ChangePrice(...)` → сохранить |
| Product | проверить правила и изменить себя |
| Repository / EF | найти, какие поля изменились, и выполнить `UPDATE` |

**Антипаттерн:** анемичная модель (Anemic Domain Model): сущность — только данные с публичными сеттерами, вся логика в сервисе. Работает для простого CRUD, но правила размазываются по сервисам и их легко обойти.

**Принципы:** Tell, Don't Ask («скажи объекту, что сделать, а не спрашивай данные, чтобы решить за него»), Information Expert из GRASP (логика там, где данные), инкапсуляция.

**Про названия:** в DDD сущность называется просто `Product` (Entity). Слово `Model` в .NET обычно означает DTO для API (`ProductDto`, `CreateProductRequest`) — такие классы у нас будут в Application.

## 5. Тонкости и улучшения: что и когда добавлять

Это не обязательные вещи, а улучшения. Принцип: **сначала база работает, потом улучшаем**. Каждую тонкость вводим, когда появляется проблема, которую она решает.

### Сейчас (Domain), если хочется
| Тонкость | Что это | Зачем |
|---|---|---|
| Фабричный метод `Create` | `public static Product Create(...)` + `private` конструктор | понятное имя; позже — возврат `Result` вместо исключения |
| Нормализация ввода | `name.Trim()` перед проверкой и записью; `Sku` → `ToUpperInvariant()` | `"  Телефон  "` и `"Телефон"` — одно и то же; `ab-1` и `AB-1` — один артикул |
| `Guid.CreateVersion7()` (.NET 9) | вместо `Guid.NewGuid()` | v7 упорядочены по времени → индекс в БД не фрагментируется, вставки быстрее |
| `sealed class Product` | запрет наследования | класс не задуман для наследования; явное намерение. ⚠️ мешает lazy-loading прокси EF — мы их не используем |
| Базовый класс `Entity` | общий `Id`, равенство по `Id` (`Equals` / `GetHashCode`) | не дублировать `Id` в каждой сущности; два объекта с одним `Id` — один товар |
| Guard-помощник | статический класс `Guard.AgainstEmpty(...)`, `Guard.AgainstNegative(...)` или пакет `Ardalis.GuardClauses` | меньше одинаковых `if ... throw` в разных сущностях |

### На шагах 1.2–1.5
| Тонкость | Когда | Зачем |
|---|---|---|
| `TimeProvider` вместо `DateTime.UtcNow` | 1.5 (тесты) | в тестах можно «заморозить» время и проверить `CreatedAt` / `DeletedAt` точно |
| `HasPrecision(18, 2)` для `decimal` | 1.2 | иначе точность цены в БД зависит от провайдера |
| Фильтрованный уникальный индекс на `Sku` | 1.2 | мягко удалённый товар не должен навсегда занимать артикул |
| Оптимистическая блокировка (`xmin` в PostgreSQL / `RowVersion`) | 1.2 | два одновременных изменения: второе получит ошибку, а не молча затрёт первое (см. вопрос 10) |
| `AsNoTracking()` для чтения | 1.3 | GET не меняет данные → не нужно отслеживать изменения, быстрее |
| `CancellationToken` во всех async-методах | 1.3–1.4 | клиент закрыл запрос → запрос к БД отменяется |

### На этапах 2–5
| Тонкость | Когда | Зачем |
|---|---|---|
| Strongly typed IDs (`ProductId` вместо `Guid`) | после этапа 1 | компилятор не даст передать `CategoryId` туда, где ждут `ProductId` |
| Value Objects (`Money`, `Sku`) | после этапа 1 | правила формата живут в типе, а не в каждом методе |
| Result pattern вместо исключений | этап 3 | ошибки бизнес-логики — ожидаемый результат, а не исключительная ситуация; исключения дорогие |
| Domain Events (`PriceChanged`, `ProductDeleted`) | этап 4 | сущность сообщает «что произошло», а другие сервисы реагируют |
| `DeletedBy`, `UpdatedBy` | этап 2 | когда появятся пользователи — кто удалил / изменил |

### Почему не всё сразу
- **Перегрузка.** Пять новых понятий за раз запоминаются хуже, чем одно, применённое на практике.
- **Без проблемы непонятна польза.** `TimeProvider` выглядит лишним, пока не попробуешь протестировать `CreatedAt`. Блокировка — пока не увидишь, как два запроса затирают друг друга.
- **Это компромиссы, а не «правильно / неправильно».** Публичный конструктор — нормальный вариант; `Create` — другой нормальный вариант.

## 6. Вопросы на подумать

Ответь своими словами — это частые вопросы с собеседований.

1. Почему `Product` хранит `CategoryId`, а не объект `Category`?
2. Почему `ProductImage` можно хранить внутри `Product`, а `Category` — нет? *(подсказка: aggregate root; главная картинка)*
3. Зачем EF Core `private` конструктор без параметров?
4. Почему `DateTime.UtcNow`, а не `DateTime.Now`?
5. Почему `RemoveStock(3)` лучше, чем `SetStock(stock - 3)`, вызванный из сервиса?
6. Почему в конструктор нельзя передавать `isDeleted` и `createdAt`?
7. Чем богатая модель отличается от анемичной? Когда анемичная модель — нормальный выбор?
8. Как EF Core понимает, какие поля изменились, если сервис просто вызвал `product.ChangePrice(...)` и `SaveChanges()`? *(ключевое слово: Change Tracker)*
9. Почему `ValidateStock` (≥ 0) и `ValidateQuantity` (> 0) — разные правила? Что пойдёт не так, если в `RemoveStock` передать `-5`?
10. Почему остаток не стоит менять через общий PUT вместе с названием и ценой? *(подсказка: два запроса одновременно — менеджер правит описание, а склад списывает товар)*
11. Почему мягкое удаление, а не `DELETE FROM Products`? Какие у мягкого удаления минусы?
12. Почему `Delete()` не вызывает `EnsureNotDeleted()`, а все остальные изменяющие методы вызывают?
